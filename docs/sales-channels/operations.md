# Operations

## Deploying safely

Nothing here is deployed to production by this work, and no production data is read or changed. When you deploy:

1. **Back up the database first.** The migrations are additive (new tables, and nullable columns on the module's own tables; every `Schema::create` and every added column is guarded; no platform table or column is altered; no foreign key points into a core table) but a backup is the rule for any release.
2. **Never run `php artisan migrate` on an empty database** (project rule): import the dump first.
3. **Prerequisite:** the Torod Point / M5AZN fulfilment tables (`2026_11_05_100000_create_provider_fulfillment_tables`, already in the project) must exist: the modules read `provider_fulfillments`, `provider_fulfillment_items` and `provider_product_mappings`, and until they do every page and scheduled command says the migrations have not been run. Then run exactly these eleven migrations, in this order (they can be run alone; the module requires all of them but the last: until they have run, every page says the migrations have not been run; the last one, the purchase-order source's columns, is **not** required: nothing in the module needs it until that source is switched on, and the source says so while it is missing):
   ```bash
   php artisan migrate --path=database/migrations/2026_11_07_100000_create_operational_cost_tables.php
   php artisan migrate --path=database/migrations/2026_11_07_100100_create_sales_channel_tables.php
   php artisan migrate --path=database/migrations/2026_11_07_100200_create_inventory_and_routing_tables.php
   php artisan migrate --path=database/migrations/2026_11_08_100000_add_state_before_dispute_to_operational_cost_entries.php
   php artisan migrate --path=database/migrations/2026_11_09_100000_add_refund_columns_to_external_order_lines.php
   php artisan migrate --path=database/migrations/2026_11_09_100100_add_charge_matching_to_sales_channel_events.php
   php artisan migrate --path=database/migrations/2026_11_09_100200_create_operational_cost_return_decisions_table.php
   php artisan migrate --path=database/migrations/2026_11_09_100300_add_basis_to_operational_cost_reconciliations.php
   php artisan migrate --path=database/migrations/2026_11_09_200000_create_channel_order_dispatches_table.php   # the claim table of dispatch.md: like the others, the module says "not migrated" until it has run (dispatching itself stays off)
   php artisan migrate --path=database/migrations/2026_11_10_100000_add_stock_allocation.php
   php artisan migrate --path=database/migrations/2026_11_11_100000_add_purchase_order_sources_to_cost_tables.php   # nullable columns on the module's own layer, invoice and invoice-line tables and one unique key on the layers; writes no data, touches no platform table; nothing uses it until OPERATIONAL_COSTS_SOURCE_PURCHASE_ORDERS is shadow or on
   ```
   Until they have run, every admin page of the module says so, and every scheduled command prints "the sales-channel migrations have not been run yet" and exits successfully.

   **The audit trail is the platform's, not this module's.** Every audited action (an account change, an approved invoice, a return decision, a reversal) is written through the platform's `AuditLogger`, which records nothing, silently, when the database has no `audit_logs` table, and no migration of this repository creates that table (it comes with the platform's own database). Check that it exists before relying on the trail: without it the module works the same, and the return decisions are still kept in `operational_cost_return_decisions` (who, when, how many, where), but there are no audit lines.
4. **Leave the switches off** (the default). `.env` needs nothing; the optional values are `SALES_CHANNELS_ENABLED`, `SALES_CHANNELS_EXTERNAL_WRITES_ENABLED`, and the cost module's two, `OPERATIONAL_COSTS_ENABLED` and `OPERATIONAL_COSTS_SCHEDULE_ENABLED` (all read with `FILTER_VALIDATE_BOOLEAN`: `off`/`no` mean off). **After the migrations nothing calculates by itself**: no FIFO consumption, no cost entry, no storage charge, and the scheduler has no cost entries, until the owner switches the cost module on (next section). `OPERATIONAL_COSTS_BASE_CURRENCY` defaults to the fulfilment currency (SAR).
5. `php artisan optimize:clear`. The scheduler (the server cron `* * * * * php artisan schedule:run`) already exists for the platform; the channel entries need nothing else, and the cost entries appear only when both cost switches are on. There is no queue worker to change: the module runs from commands.
6. Give the roles that should see the screens the two new permissions, **Sales Channels** and **Operational Costs** (the master admin has them).

### Switching the cost module on (the order)

1. Enter what the costs are built from, as a person: contracts, purchase invoices (or opening stock on the *Product costs* screen). Nothing needs the switch for this. A marketplace invoice that bills a fee as one total for a month may be approved now: while the statements are only stored it is posted in full, and once the master switch is on the catch-up cancels that posting and sets the line against the statements, so the fee is counted once (see [costs.md](costs.md), *One charge, one cost*).
2. **Master switch**: `OPERATIONAL_COSTS_ENABLED=true` in `.env`, then `php artisan config:clear`. From now on a finance import run posts what it reads, and `php artisan costs:post-pending-fees` posts what was stored while the module was off (exactly once; running it again posts nothing), takes back the statement rows an API fee repeats and sets the approved invoice lines against the statements. Run `php artisan costs:refresh --days=365` once for the sales that existed before. Returned units can only be put back once their cost of goods has been recognised, so this step comes before the returns procedure below.
3. **Schedule**: only after the figures look right, `OPERATIONAL_COSTS_SCHEDULE_ENABLED=true` and `php artisan config:clear`. `costs:refresh --days=3` (hourly) and `costs:accrue-storage` (daily) are then on the scheduler. It has no effect while the master switch is off.

### The purchase-order source (optional, and the owner's decision)

Off by default and independent of the schedule. The platform's tables (`purchase_orders`, `purchase_order_items`, `suppliers`, `stock_movements`) are only ever read, and they are **inferred**, not verified: do this on a restored copy of the real database first ([rehearsal-on-a-copy.md](rehearsal-on-a-copy.md)).

1. Run the tenth migration (above) and `php artisan costs:reconcile-platform` with the master switch on: it needs nothing else and writes nothing. Read what it says about the lines that cannot be layered (and why), the stock no layer covers and the products whose layers and stock disagree.
2. `OPERATIONAL_COSTS_SOURCE_PURCHASE_ORDERS=shadow`, `php artisan config:clear`, then `php artisan costs:layers-from-purchase-orders --since=YYYY-MM-DD` (a dry run): it lists the layers it would make and writes nothing, anywhere.
3. Decide the cutover date, and enter the opening balance for the stock on hand at it (the *Product costs* screen). Replaying all history without it would count units that were sold long ago.
4. `OPERATIONAL_COSTS_SOURCE_PURCHASE_ORDERS=on`, `php artisan config:clear`, `php artisan costs:layers-from-purchase-orders --apply --since=YYYY-MM-DD`. Run it again whenever goods have been received (it makes nothing the second time for the same units); it is audited (`operational_cost.layers_from_purchase_orders`). With the source on, a purchase invoice line can name the purchase-order line it bills (it then makes no second layer and records a variance), and one that looks like goods already received holds the invoice until a person looks.
5. To switch it off again, set `off` and clear the configuration: layers already made stay (they are ordinary layers), nothing new is made, linked invoices that were not approved yet cannot be approved until it is on again or they are voided.

A cached configuration (`bootstrap/cache/config.php`) makes an edit of `.env` inert until `php artisan config:clear`; the project's deployment guide forbids `config:cache` on this platform. To switch the cost module off again, set the value to `false` (or remove it) and clear the configuration: nothing that is already in the ledger is touched, and the statement postings read afterwards wait for the next time it is switched on. The cost screens show a banner while the master switch is off and another while only the schedule is off, and the Sales Channels hub lists both switches.

**How the code gets there** is the project's own overlay procedure as `docs/integrations/pilot-deployment.md` lays it out: `scripts/deploy/build-overlay.php`, a full backup with `backup.sh`, `deploy.php verify`, `php artisan down`, `deploy.php apply`, `php artisan optimize:clear` and a PHP-FPM / OPcache reload, `php artisan up` (the new code is dormant until the migrations run); then, as a separate later step, the eleven migrations above with their paths (the guide recommends `down` and a database-only backup before them and `up` after). Files are rolled back with `deploy.php rollback` (it restores replaced files and deletes added ones).

**Rollback:**
* `SALES_CHANNELS_ENABLED` is read from `.env` (through `config/sales_channels.php`) when a PHP process starts: switching it off and running `php artisan config:clear` (or `optimize:clear`) stops every external call of each process that starts afterwards. With a cached configuration (`bootstrap/cache/config.php`) an `.env` edit changes nothing until the cache is cleared; the project's deployment guide forbids `config:cache` on this platform and checks that it is absent. No test reads the switch from `.env`; a run already going keeps the value it started with (to stop that one at once, disable the account or forbid writes in the panel: the next call obeys). It stops nothing else: the cost commands have their own two switches (above), `channels:prune` has none (it posts nothing; remove its line from `ScheduleDefinition` to stop it), and Trendyol webhooks that arrive are still authenticated and stored (outcome `ignored_capability_off`).
* The tables can stay (nothing is read from them by anything outside the module) or be dropped. Each `php artisan migrate --path=…` is its own batch, so `migrate:rollback` takes back only the last one: roll back each migration with `--path`, in reverse order, **while its file is still on the server**; only then restore the files with `deploy.php rollback`, which deletes the files the release added (the migration files among them), after which `migrate:rollback` finds nothing to undo ("Migration not found"). The `down()` methods are tested by calling them directly on a reconstructed test schema (table and column names; not column types or indexes), not through `migrate:rollback`. Dropping deletes the modules' own data for good (accounts with their encrypted credentials, the ledger) and does not undo what they wrote into platform tables (audit-log lines, the two permission keys in the roles). Rolling back the refund columns discards the refunded amounts they hold (the refund events stay stored and marked applied, so a later migration does not re-apply them by itself), and rolling back the return-decisions table discards the record of which returns were put back (the cost layers and ledger entries the decisions made stay).
* LWA (Amazon): the client secret has to be rotated every 180 days and developer access is deactivated after 90 days without a successful call (Amazon's rules); the refresh token is valid for 365 days. Nothing here tracks their age or warns before they run out: the account is marked as needing re-authorisation when Amazon refuses it, and a 403 caused by an expired secret can read as "probably lacks a role".

## Connecting a channel (step by step; each step is an admin decision)

1. *Sales Channels → Add account.* Enter the seller id, the credentials (write-only; the page only ever says set / not set), the environment (sandbox/stage or production), the market settings. The account is created **disabled**.
   * **Amazon:** a private-developer application with the roles in [api-reference.md](api-reference.md), self-authorised in Seller Central → the LWA client id/secret and the **refresh token**; the seller id (Merchant Token); the marketplace id (Saudi Arabia `A17E79C6D8DWNP`); region `eu`.
   * **Trendyol:** the Seller ID, API key and secret (Account Information → Integration Information; stage and production differ), storefront `SA`, an integration name (letters/digits, ≤ 30). For stage, ask Trendyol to allow the server's egress IP.
2. Enable the account, switch **Connection Test** on, press *Test connection*. It only reads. The result lists granted and missing permissions; fix roles/keys and test again.
3. Switch on **Read-only Sync**, then **Product Sync**, **Order Import**, **Financial Reconciliation** as needed. Each is a separate decision; a successful test never switches anything on.
4. Link listings to products (*Products & Channels*): nothing is linked automatically unless the account's explicit *auto-link exact SKU/barcode* setting is on; names are never matched. The default stock locations (Torod Point, M5AZN, the own warehouse; an Amazon FBA location per Amazon account) exist from the first time a module page is opened or a scheduled command starts after the migrations. *Stock by location* shows what each one holds, one location at a time, with how far each figure can be trusted: Amazon FBA is shown on its own and is never added to Torod Point's.
5. Add **routing rules** (*Dynamic Routing*). With no matching rule the account's default decides: *manual review* (every order waits for a person — the standard) or *managed by someone else* (the order is only followed, for an account whose shipments another integration creates). Set it on the account's page.
6. Writes (**Inventory Publishing**, **Price Publishing**, **Fulfillment Dispatch**) additionally need: the environment switch on, *write enabled* on the account, a recorded approval with a reason, and dry run turned off. Start with dry run on: it logs the exact request and sends nothing.

## Running things by hand

```bash
php artisan channels:status                         # switches, accounts, capabilities, last sync
php artisan channels:test-connection {account}      # harmless reads; prints granted / missing
php artisan channels:sync {account} --only=orders   # orders | returns | listings | inventory | finances; omit --only for every resource the account may read; --due runs only what the scheduler would
php artisan channels:publish {account} --only=stock,price,settle,shipments
php artisan channels:stock-use-platform-for-own-warehouse [--apply]   # make the own warehouse read the storefront's stock (a dry run unless --apply; audited; needs SALES_CHANNELS_OWN_WAREHOUSE_SOURCE=platform)
php artisan channels:publish --only=allocate        # after an order import: divide the pools whose orders changed and send what LOWERS a quantity (scheduled two minutes after each order import)
php artisan channels:import-statement {account} statement.csv   # a statement exported from the seller portal (columns in the command's class docblock); says how many rows the API had already given (skipped) and how many may overlap with it
php artisan costs:refresh --days=7                  # bring cost entries of the sales placed OR changed in the last days up to date (a sale delivered, shipped or cancelled later is picked up when it changes); needs OPERATIONAL_COSTS_ENABLED
php artisan costs:accrue-storage --date=2026-11-05  # storage cost of one day; needs OPERATIONAL_COSTS_ENABLED
php artisan costs:post-pending-fees [account]       # post the statement fees stored while the cost module was off (or that the database refused once); each exactly once
php artisan costs:reconcile-platform [--json] [--limit=50] [--product=ID]   # READ-ONLY: where the cost layers and the platform's purchase orders, stock and store orders disagree (needs OPERATIONAL_COSTS_ENABLED; writes nothing)
php artisan costs:layers-from-purchase-orders [--dry-run|--apply --since=YYYY-MM-DD] [--product=ID] [--line=ID] [--json]   # MANUAL ONLY, never scheduled: cost layers from the goods the platform received on its purchase orders; a dry run unless --apply; --apply needs OPERATIONAL_COSTS_SOURCE_PURCHASE_ORDERS=on, the master switch and the cutover date
php artisan channels:dispatch                       # turn routed orders of automatic accounts into provider shipments (see dispatch.md; nothing unless every switch is on)
php artisan channels:dispatch-sync                  # read the provider shipments back onto the dispatched channel orders
php artisan channels:purge-buyer-data               # remove buyer details that are no longer needed (runs whatever the switches say)
php artisan channels:find-shipments                 # find shipments a provider created directly (off until SALES_CHANNELS_SHIPMENT_DISCOVERY_ENABLED)
php artisan channels:prune --days=60                # delete old call logs and clear the stored text of old webhook deliveries (daily on the schedule; the orders and costs they led to are kept)
```

**History:** the scheduled refresh looks at the last three days, so the sales that existed before this module was deployed have no cost rows. They are shown as costs-not-yet-determined (their profit is provisional, never a perfect margin) until `php artisan costs:refresh --days=365` (or the span wanted) has run once. Recognising the cost of goods of old delivered orders takes units from the FIFO layers, so enter the purchase invoices (or the opening stock) first; a sale whose goods have no layer to take from is reported as a shortfall, not as free.

With `OPERATIONAL_COSTS_ENABLED` off the three `costs:*` commands print one line naming it, write nothing and exit successfully; `channels:import-statement` still stores the rows and says how many postings wait.

`costs:refresh` and `costs:accrue-storage` isolate each sale (each warehouse): one that cannot be brought up to date is reported to the log and counted, the others are still looked at, and the command exits with a failure so the scheduler shows it.

Each prints `ok`, `skipped` (switch/capability off), `busy` (another run holds the lease or the resource is backing off), `rate_limited` or `failed`. A failed resource backs off (5 minutes per consecutive failure, capped) and never advances its watermark; the next successful run re-reads from the watermark less 10 minutes and records nothing twice.

A backlog larger than one allowance is read over several runs: when the channel (or our own limiter) says wait, the place reached is saved before the run backs off, and the next run goes on from it. A statement is read in windows of at most 180 days (a longer gap takes several runs; the watermark only moves as far as was read), and a run that goes on from a saved place asks for the very window it was saved with. A snapshot of stock the channel holds for us (Amazon FBA) is always read in one go: its page tokens live seconds, so a saved one is never used.

**Stopping a run that is already going:** switching the account off, forbidding writes, going back to a rehearsal or withdrawing an approval takes effect at the very next call the run makes (the transport reads those five switches from the database before every call, not from the account the run started with).

## Dividing one stock between the channels

Several listings (of one account or of several) can offer the same physical stock: that is one POOL, a product (or one variant of it) at one location. What all of them are shown never adds up to more than the pool's net, which is the location's figure less the units held by open channel orders, less the store orders the provider has not counted yet, less the pool's buffer (`PoolNet`).

* **Who gets what.** The storefront's reserve comes off first (default none; a pool can name its own, in units or as a percentage). Then, from what is left: listings with a fixed number of units, listings that fill by priority up to their maximum, listings with a percentage, and an equal split among the rest (a listing that cannot take its part gives it back to the others). Everything is rounded down once, at the end, and what rounding leaves over stays with the storefront; a bigger net never gives a listing less. A listing is never shown more than its maximum, and its own buffer is taken off its part. Set a listing's share in *Products and channels → Publishing settings*; a policy (account or product) can carry the same fields and the listing's own value wins.
* **One writer.** The division of a pool is worked out under the pool's row lock (`inventory_pools`), from inputs read after the lock was granted, and the result is checked before it is kept (the reserve and the parts never exceed the net: a division that does fails the run instead of being sent). The pool's version moves only when the division changes. The publisher plans every listing from it, checks the version again under the lock just before the call and plans again when another process moved it. Nothing here locks `products`.
* **When a quantity is raised.** Never above what the channel itself showed when it was read after our last write and is lower than what we wrote (it sold the difference), unless the pool has more than when we wrote; never while the order import of any account offering the pool is older than `SALES_CHANNELS_STOCK_ORDER_FRESH_MINUTES` (default 15; an account that has never imported an order has nothing to be late); never while the pool is promised more than it holds, nor for `SALES_CHANNELS_STOCK_DEFICIT_BLOCK_CYCLES` computations after; and never before the listings that give units up have been lowered. A lowering is always sent. Each refusal is a skip reason on the publish result (`order_sync_stale`, `deficit_block`, `awaiting_siblings`).
* **A deficit** (more promised than the pool holds, because a store order or an order of another channel arrived after the stock was offered) offers nothing from the pool until it clears. The module never cancels an order: the orders holding the pool are for a person to look at.
* **The quick run.** Importing, changing or cancelling an order marks its pools. Two minutes after each order import `channels:publish --only=allocate` divides the marked pools again and sends only what lowers a quantity, and only when the drop is at least `SALES_CHANNELS_STOCK_REDUCTION_DEAD_BAND_PERCENT` of what is shown or the quantity left is at most `SALES_CHANNELS_STOCK_REDUCTION_ALWAYS_BELOW_UNITS` (so a channel's rate limits are not spent on a small drop of a large quantity). A raise waits for the regular run. It uses the account's stock lease: it never overlaps the regular run.
* **The margin for what a channel sells before we hear of it** (`SALES_CHANNELS_STOCK_LAG_WINDOW_MINUTES`, default 0 = off): a channel that has been selling is shown a little less, in proportion to its sales of the last `SALES_CHANNELS_STOCK_LAG_RATE_MINUTES` over the time that passes before its orders are imported. Switching it on trades some quantity for safety; the suggested value is 20.
* **Every value** (all environment-backed, read at process start; `config:cache` is not used): `SALES_CHANNELS_STOCK_ALLOCATION_ENABLED` (true), `SALES_CHANNELS_STOCK_STOREFRONT_RESERVE_MODE` (`percent`) and `_VALUE` (0: the reserve kept for the storefront when a pool names none; 50 percent is the suggestion while the storefront sells the product), `SALES_CHANNELS_STOCK_ORDER_FRESH_MINUTES` (15), `SALES_CHANNELS_STOCK_LAG_WINDOW_MINUTES` (0 = no margin), `_LAG_RATE_MINUTES` (120), `_PUBLISH_INTERVAL_MINUTES` (15, the schedule's), `SALES_CHANNELS_STOCK_DEFICIT_BLOCK_CYCLES` (2), `SALES_CHANNELS_STOCK_REDUCTION_DEAD_BAND_PERCENT` (10), `_REDUCTION_ALWAYS_BELOW_UNITS` (10), `SALES_CHANNELS_STOCK_AGED_HOLD_DAYS` (7: the hub lists older reservations of open orders), `SALES_CHANNELS_STOCK_RELEASED_RESERVATION_DAYS` (30: `channels:prune` deletes older released reservations). A pool's own reserve and buffer are set through `PoolSettings` (validated, audited, no screen yet).
* **Rolling back.** `SALES_CHANNELS_STOCK_ALLOCATION_ENABLED=false` (then `php artisan config:clear`) offers every listing the pool's whole net again, as before; no pool row is written and no order marks one. The new tables and columns can stay.
* **What it cannot do.** The storefront still sells from `products.current_stock`, which no channel order and no division lowers: the channels together stay within the pool's net, the storefront and the channels together can not be bounded without a change to the storefront's own stock (not made). Stock the store owns itself (a location whose source is the platform) is refused until the owner decides how channel units leave it. A sale a channel made and we have not imported yet is a window no code can close; the margin above and the freshness rule narrow it.

## The own warehouse read from the storefront's stock

Nothing writes the own warehouse's balances today, so it reads `unknown` and offers nothing. With `SALES_CHANNELS_OWN_WAREHOUSE_SOURCE=platform` (default `manual`) and the audited command `channels:stock-use-platform-for-own-warehouse --apply` (a dry run without `--apply`; it refuses while the switch is off and is safe to repeat), the location's source becomes the platform and `LocationStockReader` reads the storefront's own stock through, one product at a time, never copying and never writing: a product without variants is its `current_stock` (negative reads as 0), a variant is its own quantity, and what the store does not count in units is unknown (a digital product, unlimited stock `999999999`, a product a provider holds, a variant that is not there, the whole of a product sold per variant). The figure is confirmed as of the moment it was read; *Stock by location* pages through the store's own products (a variant product is one row per variant). Neither the switch nor the command is run by anything else: the row is never changed automatically.

* **Nothing is offered from it yet.** Stock the store owns is refused (`storefront_owned_needs_owner_decision`): the store already takes its sales off `current_stock`, and no channel order lowers it, so the units a channel sold would stay on offer. Deciding how channel units leave the storefront's stock (a locked, flagged decrement like the checkout's, which conflicts with the provider sync and the typed-stock paths) is the owner's; no code here writes `products.current_stock`. Until then the read-through feeds the screens and the routing check only.
* **A shipped channel order's units keep counting.** A live read makes the "count taken after the order shipped" rule meaningless (it is always taken after), so for this location a committed reservation counts until the storefront's stock has been lowered for it: `inventory_reservations.applied_to_platform_at`, honoured only with `SALES_CHANNELS_APPLY_CHANNEL_ORDERS_TO_PLATFORM_STOCK` on, which nothing in this version sets (it is off, and nothing writes the mark). Until the owner decides, such a unit counts until its order is released: the pool is under-offered, never over-offered. A channel order the application turned into an internal order is a store order: its hold is released and the store's own decrement counts it.

## Webhooks (Trendyol)

Registering is a write (needs *Order Import*, the *webhook management* approval, write enabled, dry run off). The address is `https://<your host>/api/sales-channel-webhooks/{account id}` (it deliberately does not contain the word "trendyol": Trendyol refuses addresses that do). Trendyol authenticates with an API key the application generates and stores encrypted; it arrives in `x-api-key` and is compared in constant time; any authentication failure is the same flat 401. Events are stored once and applied through the same idempotent path the poller uses; polling stays the source of truth because Trendyol documents webhook delivery as not guaranteed.

## Returns and refunds (what to do when units come back)

The model is in [costs.md](costs.md) (*Refunds and returns*). In daily work:

1. **Refunds need nothing from you.** A refund the channel reports (Amazon refund transactions, Trendyol claims) reduces the revenue of its order line the next time the finances (or returns) are read. A refund of an order that is not held yet waits (`needs_review`, *the order is not held*) and is applied when the order arrives; one whose item matches no single line, or that is in another currency than the order, waits for a person: look at it in *Sales Channels → Logs → events*.
2. **Units that came back are a decision.** Open *Operational costs → Returns awaiting a decision* (the overview shows how many wait; the orders list filters on *Awaiting a restock decision*). For each return, once the parcel has been looked at:
   * **Trendyol**: the claim the channel accepted is listed with its units. Enter the units to **put back on the shelf**, the **damaged units to write off** (the two must add up to the claim's units) and the **location** the units go back to (the line's own is offered), then *Record the decision*. If the channel accepts another item of the claim later, the unit it gained is listed again, with a form of its own, and is decided the same way.
   * **Amazon**: Amazon's returned units are not read. On the order page of a shipped order, use *Return received* on the line: the units to put back, the damaged units to write off, the location. If two people open the form for the same parcel, one unit goes back, not two (the second finds it recorded); a form opened before another record was made says the line changed: reload the page and look at what was recorded.
   * A unit put back re-enters stock at the cost it left at and that part of the cost of goods is reversed; a unit written off creates no layer and its cost of goods stays in the profit. Pressing the button twice changes nothing; the decision is audited with your name.
3. **What the form refuses**, and why: more units than were sold or than were taken from stock for the line; a claim not decided for all its units (or all the units it gained); a form that is out of date (the line changed since it was opened); a location that is not an active location of the order's seller; a line not linked to a product; an order whose cost of goods was never recognised (it has not shipped, or the cost module was off), for which only a write-off is possible. Fix the cause (link the line, run `costs:refresh`, switch the module on) and decide again.
4. **Permission.** Deciding needs *Operational Costs*, and so does the switch below: a role with only *Sales Channels* sees the returned units on the order page without the form, and sees the account's switch as it is, not changeable.
5. **Automatic put-back is the owner's decision.** The Trendyol account setting *Put units of accepted returns back on the shelf automatically* is off by default. Switch it on only if the owner accepts that **every** unit of an accepted claim goes back on the shelf at its original cost, damaged or not, at the location the line was sold from, without anyone looking. It does nothing while the cost module's master switch is off; claims it cannot decide yet stay on the list for a person. It is audited as automatic. Switching it off stops new automatic decisions and undoes none. A sale that is cancelled after some of its units were put back takes those units off the shelf again (the cancellation gives all of the sale's units back).
6. **Store orders** are not part of this: a store refund reduces the revenue as before and the module does not put its units back.

## When something looks wrong

| Symptom | Look at |
|---|---|
| nothing syncs | `channels:status`: global switch, account enabled, capability, backing-off resource, connection `auth_expired`/`revoked` |
| an order is "waiting" | the order page → latest decision and its reason code (`no_rule_matched`, `cod_requires_review`, `unmapped_lines`, `managed_dispatch_not_available`, …) |
| costs show "Missing" | the reason on the entry (`no_contract`, `awaiting_channel_statement`, …): set up the contract or wait for the statement |
| a refund does not reduce the revenue | *Logs → events*: a refund event says why it waits (`order_not_held`, the item matches no single line, another currency, an amount of a part nobody classified); it is applied by itself when the cause goes away, and never to a line that cannot be told |
| an invoice line is "compared" and nothing of it is in the ledger | it bills a fee as one total for a month and the channel's statements already booked that fee in that month: its row is in the invoice (basis *statements*), a match or a variance for a person. If the statements were later reversed by a person, press *Reconcile* on the invoice |
| returned units are not on the shelf | *Operational costs → Returns awaiting a decision*: nobody has decided them yet (or the owner's automatic setting is off); a decision that is refused says why on the page |
| a statement row did not add a cost | the import said it was skipped: the API had already given the same charge (a `duplicate` event in the logs); a row marked *may repeat a charge the API gave* (`possible_overlap`) is counted until a person decides |
| a publish keeps failing | the listing's publish state; a value the channel refused three times (right away, or later in the batch result, or accepted and never applied) is not sent again while it is the requested value (any different value is sent at once and starts a new count; nothing lifts the stop by hand); an outage or a dropped connection never counts against the value and is simply tried again |
| a follow-up says "could not be read" | a batch result the channel would not give right now (a switch is off, the channel is busy, the batch is gone): the change stays queued and the other batches are still followed |
| stock offered is lower than the shelf | open channel orders hold their units (*reservations*); they come back when the order is cancelled, and a shipped order counts only until the location's own count shows it. Store orders the provider has not counted yet, the pool's buffer and the other listings that share the stock are taken off too: the listing's *Stock by location* row shows each figure |
| a quantity is not being raised | the publish result's skip reasons: `order_sync_stale` (an order import is behind: look at the account's *orders* resource), `deficit_block` (the pool is, or just was, promised more than it holds), `awaiting_siblings` (another listing of the same stock still shows more than its part: it is lowered first) |
| stored credentials "cannot be decrypted" | this server's application key differs from the one that encrypted them: restore the key (nothing was overwritten), or enter the complete set of credentials again to replace them |
| a Trendyol tracking push fails | the order's `channel_notify_error` (a carrier with no Trendyol code in the account's *carrier codes* is one cause); after three consecutive failed writes for the same tracking number (a refusal other than 401/403, a 5xx, a timeout, a 429, any Amazon answer other than 204 except 401/403, or a Trendyol package that has left Created/Picking/Invoiced) it stops until a person presses *Tell the channel about this shipment* or the tracking number changes; with the 15-minute schedule about 45 minutes of failing writes is enough (for Trendyol only while the read of the package that precedes the write still succeeds). An exception (a carrier with no code, a failed read of the package, which includes a whole-channel outage on Trendyol, or a 401/403 on the write itself) is not a refusal: it clears the count and is retried every cycle without ever stopping |

## Known limits of this version

* The Amazon marketplaces of one account are read one after the other (orders take them all at once); listings, FBA stock and statements go through every marketplace id the account holds, and each has its own place in a paused sweep.
* An invoice with thousands of lines is linked to provider shipments one line at a time against the Fulfilment tables, whose secondary reference and tracking columns are not indexed (they belong to the Fulfilment workstream; this module indexes its own tables).
* A deadlock is retried (three tries in all, outer transaction only) in order ingestion, lease taking, ledger writes, invoice approval and FIFO layers; routing, shipment linking, return ingestion, credential saving, contracts, dispute resolution and cost allocation are not retried. No test runs the retry loop or a real deadlock (two tests only make a replaced `CostLedger::record()` / `ChannelOrderIngestor::ingest()` throw a deadlock-shaped error to show that the next run or redelivery recovers). The multi-process tests in `tests/Feature/Concurrency` (MySQL and MariaDB only) now run the first-write races of order ingestion, reservations, the pool rows and the lease row for real: the same order read by five processes at once is one order and one hold, six processes dividing one pool give one division, and six processes asking for one lease are given it once (taking a lease for the first time used to fail with a duplicate-key error for the loser: fixed). The fallbacks of routing decisions, the ledger, invoices and FIFO layers that catch a unique-index violation are still reasoned about only.
* The instants of an order are stored truncated to the second (fractions are dropped, not rounded): of two changes to one order inside the same second the later wins only if its time is later than the stored second, so a stale update from that same second can be applied over a newer one; and the stale-update check does not run at all when the channel sends no modification time. Only an update two hours older is tested. Nothing in the module depends on finer ordering.
* A rehearsal (dry run) does not remember what it rehearsed, so every cycle logs the same rehearsed requests again (nothing is sent: Amazon's validation preview is a PATCH with the real values and is gated like the real write).
* A publish run does not renew its lease while it works: a very long Amazon per-SKU run (thousands of listings at 5 calls a second) could outlive the 20 minutes of the lease.
* MySQL sorts the keys of a JSON column, so a stored object comes back with its keys in another order. Nothing in the module compares a stored JSON value as a whole except the fingerprint of a routing decision, which puts the keys of every line in one order first (a test stores the lines in MySQL's order and shows that no second decision is recorded).
* The application's MySQL connection uses `utf8mb4_unicode_ci`, which compares text without regard to letter case and ignores trailing spaces. Two listing keys that differ only by case would be one mapping and one unique key there, while SQLite (the daily tests) tells them apart. Nothing in the module relies on case to tell two listings apart; a seller who keeps two SKUs that differ only by case would see them merged.
* Price and quantity writes, shipment confirmation and the connection test use the first marketplace id of an Amazon account (reads go through all of them): an account that sells in several marketplaces gets its writes in the first only.
* A manual shipment link is checked against the other channel orders and against the store's own fulfilments, not against the provider: a reference that does not exist at the provider is accepted.
* The identity of a statement fact changed in this release (Trendyol rows through `Money`, statement-file rows, Amazon facts without their posted date) and nothing is backfilled: the module has never been deployed, so no environment holds an event stored under an earlier formula, and if one ever does, its settlement rows read again inside the finance sync's 3-day overlap would count twice. Start such an environment clean.
* A manual statement row that names no order and no settlement can only be matched to the API's charge by its amount and its day: with exactly one candidate it is a duplicate and is not counted; with several (or none yet) it is imported, counted and marked `possible_overlap` for a person, and the API reading the period later only marks it too. Rows that name the order (and package) or the settlement are matched exactly, and `25`, `25.0` and `25.00` are the same amount. A person still decides the ambiguous ones; see [costs.md](costs.md), *One charge, one cost*.
* Telling a channel about a shipment has no lock and no lease: the scheduled run and the *Tell the channel* button can overlap and send the same tracking number twice. A carrier with no Trendyol code is retried every cycle with a read of the package and no write until the code is set.
* Unlinking a shipment takes no lock and does not re-read the order: unlinking a stale in-memory copy of an order that has just shipped reopens its reservation until the next read of the order commits it again (a window of milliseconds; the effect can only under-offer stock).
* `sales_channels.managed_dispatch_enabled` (default off, not an environment value) makes the engine record rule decisions to create provider shipments that nothing executes; keep it off until the dispatcher exists.
* The stock offered to channels is divided between the listings that offer it (see *Dividing one stock between the channels*), which bounds what the channels are shown together by the pool's net; it does not bound the storefront and the channels together (the storefront sells from `products.current_stock`, which a channel order never lowers), and nothing can bound a sale a channel made and we have not yet imported (publishing runs every 15 minutes, orders are imported every 5, the quick run two minutes after). A channel order not yet imported reserves nothing, and a unit that sits on no pool (a line linked to no product, or whose listing and routing name no location) is taken off nowhere: `ChannelOrderReservations::unattributedUnits()` counts them. A figure a person typed counts store orders the provider accepted after it was typed. Stock the store owns itself (a location whose source is the platform) is refused with `storefront_owned_needs_owner_decision` until the owner decides how channel units leave it; nothing here ever writes `products.current_stock`.
* The first sync of orders and of financial statements reads the last 30 days only (`order_backfill_days` and `finance_backfill_days` in `config/sales_channels.php`; no environment value, command option or screen); older history needs the setting changed and published. Trendyol's `orders/stream` allows about three months, `/v2/orders` one.
* `channels:publish --only=shipments` and `--only=settle` print counters (for example `{"sent":0,"skipped":0,"failed":1}`) and exit successfully whatever those counters say (only an uncaught exception fails them); the sync and the stock/price publish exit non-zero on `failed`, and other commands have their own failure conditions.
* The Amazon connection test probes five areas; a probe that does not succeed and is not a definitive 4xx refusal (a rate limit, a server error, a timeout, an unreachable host, a redirect, 408/409/425) is recorded as `<area>:unverified(<status>)`, never as granted, and blocks approving a write until a clean test (a 401/403 is recorded by the area's name alone and another 4xx as `<area>:rejected(<code>)`; a failure of the seller probe fails the whole test). The connector tests cover 429 and 500; timeouts and unreachable hosts are classified, and tested, in the transport layer only. If one of its own allowances is used up (order search 18 an hour, shared with the order sync; seller probe 10 per 15 minutes) the test answers "try again in about N seconds" and leaves the account's status as it was.
* The routing engine decides channel orders (Amazon, Trendyol) only; store orders keep the existing Torod/M5AZN path. A decision stores the rule as it was in part only (id, name, priority, action, provider and location targets, and the channel, account, SKU and product conditions), not its other matching conditions (fulfilment mode, policy, stock location, product provider, country, city, confirmed stock, order-total bounds, cash on delivery, validity window, seller). Rules have no manual-exception condition and no available-fulfilment-cost condition; "product provider" is the provider of the listing's stock location, not `products.fulfillment_provider`.
* *Sync now* and *Publish now* on an account page run inside the web request: a slow channel can outlast the browser's or the proxy's timeout. For a long run use the artisan commands above.
