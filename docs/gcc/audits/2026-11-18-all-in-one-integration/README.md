# All-in-one CI integration of the open pull requests (2026-11-18)

**A CI-only branch, never merged, never deployed.** `gcc/release/all-integration-ci` holds every open main-based pull request of `fullstackfull/lavkoo` in one tree, so that the way they behave together is read from a test run and not guessed from their descriptions. It exists to find what breaks when the pull requests meet, before anyone merges one of them into `main`.

## What it contains

- **Base:** `gcc/release/security-gcc-integration-ci` (`f6fb03af`): the security set (PR 75, `47b78ab8`) and the GCC stack (PR 83, `8ff34109`) merged together, five files resolved by hand.
- **On top, in dependency order:** PR 1 to 7, 9 to 18, 20 to 27, 29 to 36 and PR 87 (GCC-05, the currency of a storefront). That is 82 of the 86 open main-based pull requests that existed when it was cut; the four that are not in it are the baseline hotfix line (PR 78, 81, 85, 86), which is cut from the server baseline `698aa1e` and deployed in stages, so it is never combined with the main-based set.
- **Head when this was written:** `c30390d1`. Rebuild it by taking the base and running the merges of the table below in order, then the reconciliation commits `6f6a5e52` and `c30390d1`.

## Result

- **Textual conflicts:** 15 of the 35 merges conflicted, in 32 file instances (28 different files); the other 20 merged cleanly. Every conflict was resolved inside the integration branch only: no pull request was changed to make a merge work.
- **Semantic conflicts, found only with the sets together:** a test or a document written for one pull request pins what the pull request's own base did, and a sibling pull request changes it on purpose. Each is listed below with the behaviour the combined tree has. None of them changes the code of a pull request, except where the table says so.
- **One defect of the security set found on the way and fixed:** a digital file row read without its id (an aggregate or a partial select) raised a `TypeError` as soon as it was serialized, in both modes of the private-files switch (PR 69). The fix is `4096f1be` on the branch of PR 69, with a test that fails without it. **The hotfix line carries the same code** (the hotfix port of PR 69, commit `53ba4a25`, stage 4): the stage 4 package has to be rebuilt with the fix before it is deployed, see below.
- **One accident, fixed:** a forced add put five generated framework cache files into the PR 87 merge; the repository's leak guard matched the word "password" in a service provider id. They are removed in `c30390d1`.
- **Local runs on SQLite of the groups the merges touch:** Wallet and loyalty (223 tests), Storefront, Wallet, Address, Checkout and Payment together (1,770 tests), the staff scope group (462 tests, 10 skipped as MySQL-only), the security tests of the seller APIs (542 tests): all passing at the head. **CI:** run 279 on `c30390d1` was dispatched at 07:07 UTC and had not finished when this was written; its result is added below when it is read, and nothing in this document is a claim about it before then.

## What this means for `main`

1. The sets can be merged in any order, but merging them without these reconciliations turns the CI of `main` red in the groups named above, because guards written for one set meet the behaviour of another. The reconciliation commits are `4fe8e4ea`, `244c5361`, `3c0671f5`, `8b6fff75`, `83da41fa`, `f5a565f4`, `8f3d0f38` and `6f6a5e52`; beyond the conflict resolutions themselves they are tests and one document, except three that change code: the in-transaction cents of the wallet checkout (`4fe8e4ea`), the one phone rule (`83da41fa`) and the two staff scope rule kinds with the null-id guard (`6f6a5e52`, and `4096f1be` on PR 69).
2. **The hotfix line needs the null-id guard before stage 4 is deployed.** Stage 4 (the hotfix port of PR 69) has the same service as PR 69 had, and a partially selected row serialized as JSON would raise there. The change is one line and one test; applying it to the hotfix tip changes the stage 4 package and the final tree, so the packages are rebuilt with the existing scripts and the numbers of the release plan are updated. This is a release decision for the owner and it is recorded in the register of open items; stage 0 to 3 are not affected.
3. The merge order for `main`, the by-hand files and the server preflight list are written in the owner guide and in the release plan; this document does not replace them.
