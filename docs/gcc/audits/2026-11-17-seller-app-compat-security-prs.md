## 2. How the app treats server answers (what decides every verdict)

1. Dio throws on non-2xx; every Dio repository funnels into `ApiErrorHandler.getMessage` (`app:data/datasource/remote/dio/dio_client.dart:38-63`, no `validateStatus` override).
2. 401 signs the user out only when the body has no `loginStatus`, no `errors`, no `message` (`app:data/datasource/remote/exception/api_error_handler.dart:62-84`, then `app:helper/api_checker.dart:21-43`). The seller middleware's 401 body `{'auth-001': ...}` (`main:app/Http/Middleware/SellerApiAuthMiddleware.php:90-92`) qualifies, so a not-approved or re-tokened seller is signed out. 403 never signs out.
3. 403 and 404 show `errors[0].message` or `message` as a snackbar (`api_error_handler.dart:49-61,91-98`; `api_checker.dart:45-71`). A bare JSON-string body would throw there (`containsKey`/index on a String, `:53`, `:92`). Only the pre-existing `close-withdraw-request` answers like that (`#52:app/Http/Controllers/RestAPI/v3/seller/SellerController.php:539`, same at `main:536`).
4. Other statuses (400, 422...) go through `ErrorResponse.fromJson`, which expects `errors` as a list (`api_error_handler.dart:111-116`; `app:data/model/response/base/error_response.dart:13-20`). Laravel's default 422 has `errors` as a map and would throw a TypeError. No reviewed change makes a Dio-parsed call return such a 422 (row 34).
5. Controllers compare `statusCode == 200` and ignore `status:'error'` inside a 200 (order edit, POS `product_not_available`, after-sale upload).
6. `http.MultipartRequest` call sites (registration, profile/bank, shop update, chat, delivery man, product image, digital file, after-sale) return the raw status; controllers test only for 200.
7. `updateToken` swallows every failure (`app:features/auth/domain/services/auth_service.dart:136-143`).
